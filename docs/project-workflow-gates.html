Single feature workflow

Plan, Implement, Verify, Ship, Learn

Run one /he:* command per stage. Start each stage in a fresh thread with the prior he-state.json; the stage skill handles supporting skills, state updates, validation, receipts, and parallel subagents when work can safely split.

1. PlanDecide owner, proof, risk, and readiness.
2. ImplementChange the canonical owner.
3. VerifyProve behavior and loop on blockers.
4. ShipRun the final gate and CI follow-through.
5. LearnAdd a durable guard when needed.

Automatic Work

  • Loads the required specialist skills for the touched area.
  • Updates he-state.json before and after each internal step.
  • Records findings with an owner repair stage and guardrails with command, status, evidence, and push-blocking status.
  • Uses parallel subagents when tasks are independent.
  • Validates state before any ready-yes handoff.
  • Ends with a compact receipt: stage, state path, decision, owner/proof, artifacts, blocker, next.

  1. Plan the work

    Decides scope, owner, blast radius, proof path, risk route, and whether implementation is ready.

    Invokes automaticallyTreehouse and worktree readiness for isolation; grill-me for unclear outcome, scope, proof, risk, UI flow, or visual direction; to-prd or to-issues only when the plan needs that artifact.
    Grill Me behaviorGrill Me owns session_state.md, its stage map, and the one-question loop. It asks as many one-by-one questions as needed until aligned or the user parks the unknown.
    /he:plan
Next: ready for /he:implement: yes/no

  2. Implement with touched-area skills

    Changes the canonical owner, runs deterministic owners first, and leaves lint/scanner/gate coverage where needed.

    Invokes automaticallycodebase-design when ownership is unclear; deterministic scripts/tests/hooks before fresh reasoning; touched-area skills such as React, Flutter, Appwrite, UI, Sentry, security, or performance based on the files and risk.
    GuardrailsReact/Next gets React Doctor, Fallow audit/dupes, lint, and typecheck. Flutter gets package-root dart analyze with flutter_skill_lints and tests when present. Missing repeatable checks become scripts, tests, hooks, or evals.
    /he:implement
Next: ready for /he:verify: yes/no

  3. Verify in a loop

    Runs the proof loop: tests, touched risk reviews, maintainability review, and E2E when user-visible flows changed.

    Invokes automaticallytest-quality for assertions and gaps; security/performance review when touched; thermo review before expensive UI proof; e2e last for real user-visible flows and artifacts.
    Guardrail proofRuns every guardrails[] command plus check-project-quality-gates.mjs --require-push-gate; missing or failing guardrails route back to /he:implement.
    Auto-fix loopDiagnose failures, route code changes back through /he:implement, update he-state.json, rerun only affected proof, and repeat until clean or blocked.
    /he:verify
Next: ready for /he:ship: yes/no

  4. Ship with no-mistakes

    Runs status/secrets checks, hook readiness, no-mistakes, PR evidence repair, and CI follow-through.

    Invokes automaticallyensure-worktree-ready.sh --check --require-pre-push and check-project-quality-gates.mjs --require-push-gate prove project hooks before no-mistakes; PR evidence repair handles hosted screenshots and video; CI follow-up batches fixes and reruns the fewest checks.
    /he:ship
Next: ready for /he:learn: yes
OR Next: loop complete: yes

  5. Learn and tighten

    Runs only when he-state.json has an open learning finding. If learning is empty, ship closes the loop.

    Invokes automaticallyrepeated-failure-learning captures the pattern; skill-creator updates stage skills when they are the owner; otherwise the guard goes into the narrow script, test, hook, route map, or source owner.
    /he:learn
Next: loop complete: yes/no

Guardrails

  • /he:implement starts only after /he:plan is PASS.
  • /he:ship starts only after verification is clean and work is committed.
  • State validation blocks false ready-yes handoffs.
  • Push dry-runs count only after project hooks are active and push-blocking guardrails pass.
  • Verify failures loop back through /he:implement; proof reruns after each fix.
  • Parallel subagents are used only for independent work and merge back through the active he-* stage.

Failure Loops

  • /he:plan stays in planning until missing owner, scope, proof, risk, or Grill Me alignment is resolved.
  • /he:implement loops in implementation unless owner or scope changed, then it returns to planning.
  • /he:verify sends fixes through implementation, then reruns only affected proof.
  • /he:ship uses the no-mistakes loop; code findings go to implementation, proof gaps to verify, gate evidence stays in ship.
  • /he:learn stays in learning until the durable guard owner exists and passes.
